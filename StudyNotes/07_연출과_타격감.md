## 1. 타격감 3종 세트

| 이름 | 느낌 | 구현 | 언제 |
|---|---|---|---|
| **히트스톱** | 때리는 순간 "턱" 하고 멈칫 | `Time.timeScale = 0.05` 잠깐 | 맞췄을 때, 콤보, 피니시 |
| **셰이크** | 화면이 부르르 | 카메라 위치에 랜덤 오프셋, 점점 약해짐 | 폭발, 충전 진동 |
| **킥** | 화면이 한 방향으로 "툭" 밀렸다 돌아옴 | 카메라 위치에 방향 오프셋 | 총 반동(쏜 반대 방향), 내려찍기(아래) |

비유: 히트스톱 = 영화의 **슬로모션 한 컷**, 셰이크 = **지진**, 킥 = **누가 어깨를 툭 침**.

## 2. HitFeel — 전역 타격감 관리자

### 히트스톱
```csharp
// HitFeel.cs:93
private void Stop(float duration)
{
    if (!_stopping) { _restoreTimeScale = Time.timeScale; _stopping = true; }   // 원래 속도 기억
    Time.timeScale = 0.05f;                                                    // 거의 멈춤
    _stopEndRealtime = Mathf.Max(_stopEndRealtime, Time.unscaledTime + duration);  // 더 긴 쪽 유지
}
// Update에서 현실 시간(unscaledTime)이 끝 시각을 넘으면 원래 속도로 복구
```
- **0이 아니라 0.05인 이유**: 완전히 멈추면 일부 물리·애니메이션이 이상해지고, 아주 살짝 움직이는 게 더 묵직하게 느껴진다.
- 끝 시각을 **현실 시간**으로 재는 이유: 게임 시간으로 재면 게임이 느려진 동안 타이머도 느려져서 영원히 안 끝난다.
- 여러 번 요청돼도 **누적되지 않고 긴 쪽이 이긴다** (`Max`). 10명을 동시에 때려도 10배 멈추지 않음.

### 셰이크와 킥 — 값만 계산, 적용은 카메라가
```csharp
public static float CurrentShake   // 남은 시간 비율만큼 선형으로 약해짐
public static Vector3 CurrentKick  // 처음 15%는 빠르게 밀리고, 나머지는 SmoothStep으로 부드럽게 복귀
```
킥 커브:
```
세기
 1 │  /\
   │ /  ‾‾‾‾\__
   │/          ‾‾‾\____
 0 └──────────────────────▶ 시간
    15%      나머지 85% (SmoothStep)
```
**강한 게 이긴다** 규칙: 약한 셰이크/킥은 이미 진행 중인 강한 것을 덮어쓰지 않는다.

### 카메라가 합치기 ([TopDownCameraFollow.cs:36](../Assets/Members/HJH/02.Scripts/Char/TopDown/TopDownCameraFollow.cs:36))
```csharp
_followPosition = Vector3.SmoothDamp(_followPosition, DesiredPosition(), ref _velocity, smoothTime);
transform.position = _followPosition + ShakeOffset() + HitFeel.CurrentKick;
```
- **따라가는 위치(_followPosition)와 흔들림을 따로 저장**하고 마지막에 더한다.
- 흔들림을 섞어서 SmoothDamp에 넣으면, 흔들림이 "목표"에 섞여 카메라가 엉뚱한 데로 표류한다.
- 원칙: **기준값 + 오프셋** 으로 나눠 저장하기. UI 애니메이션에서도 똑같이 쓴다.

### 스킬은 HitFeel을 직접 모른다

예: Gunner의 관통 빔 ([PiercingBeamSkillData.cs:110](../Assets/Members/HJH/02.Scripts/Char/FSM_Skill_Module/Gunner/PiercingBeamSkillData.cs:110))

## 3. DOTween으로 UI 연출 — `ComboFeedbackUI`

팀원(UI 담당)이 보고 따라 할 수 있게 **짧고 단순하게** 만든 콤보 연출 파일. (이 파일은 지금도 다듬는 중이라 세부는 바뀔 수 있음)

### 하는 일
1. 화면 가운데 "COMBO!" + 콤보 이름 (피니시면 "FINISH")
2. 콤보에 쓰인 입력 칸들이 튕김
3. 칸 밑에 콤보 이름이 잠깐 뜸
4. 콤보에 쓴 스킬 아이콘(Q/E)이 튕김

### 데이터는 창구에서만
```csharp
_hud = PlayerHudSource.Instance;
_hud.ComboLanded += OnComboLanded;
_hud.FinisherReleased += OnFinisher;
```
→ 04장의 규칙대로, 이 UI는 `ElementComboChain`을 직접 모른다.

### DOTween 기본
DOTween = "A에서 B로 시간에 걸쳐 바꿔줘"를 한 줄로 쓰는 라이브러리 (트윈 = between).
```csharp
centerGroup.DOKill();                                         // ① 이전 연출 중이면 멈춤 (겹침 방지)
centerGroup.alpha = 1f;
centerGroup.transform.localScale = Vector3.one * 1.3f;        // ② 시작값: 1.3배
centerGroup.transform.DOScale(1f, 0.15f).SetUpdate(true);     // ③ 0.15초 동안 1배로
centerGroup.DOFade(0f, 0.25f).SetDelay(0.8f).SetUpdate(true); // ④ 0.8초 기다렸다 0.25초 동안 사라짐
```

| 함수 | 뜻 |
|---|---|
| `DOScale(목표, 시간)` | 크기를 목표까지 |
| `DOFade(목표알파, 시간)` | 투명도를 목표까지 (CanvasGroup, TMP_Text, Image) |
| `DOPunchScale(세기, 시간)` | 크기가 "통!" 튕겼다 원래대로 |
| `.SetDelay(초)` | 그만큼 기다렸다 시작 |
| `.SetUpdate(true)` | ⭐ **timeScale 무시(현실 시간)** |
| `DOKill()` / `DOKill(true)` | 이 대상의 진행 중 트윈 중지 (true = 끝 상태로 즉시 완료) |

### ⭐ SetUpdate(true)가 핵심인 이유
콤보가 터지는 순간 `HitFeel`이 히트스톱(timeScale 0.05)을 건다. 기본 트윈은 게임 시간을 쓰니까 → **UI도 20배 느려져서** 배너가 안 나오는 것처럼 보인다.
`SetUpdate(true)` = "나는 현실 시간으로 움직일게" → 게임은 멈칫해도 UI는 정상 속도. (02장 "unscaled 시간"과 같은 개념)

### DOKill로 겹침 방지
콤보가 0.3초 간격으로 연달아 터지면, 이전 사라지기 트윈(`DOFade 0`)이 새 연출 위에서 계속 돌아 **새 배너가 중간에 사라진다**. 시작 전에 `DOKill()`로 이전 것을 끊는다.
`Bounce`에선 `DOKill(true)` — 이전 튕김을 **끝 상태(원래 크기)로 완료**시키고 새로 튕긴다. 안 그러면 1.2배인 상태에서 또 튕겨서 점점 커질 수 있다.

### "어느 칸이 콤보였나" 계산
```csharp
// 콤보는 항상 "마지막 입력들"로 완성된다 (06장 끝부분 매칭)
int first = Mathf.Max(0, inputs.Count - combo.Length);
for (int i = first; i < inputs.Count; i++) Bounce(inputCells[i]);
```
입력 4개, 콤보 길이 2 → 2, 3번 칸. 06장의 알고리즘을 알면 바로 이해되는 한 줄.

### 교훈 ①: 왜 단순하게 다시 썼나 — "읽는 사람 기준으로 코드 쓰기"
이 파일은 원래 411줄이었다. 연출 6개를 `[1]~[6]` 번호 구역으로 나누고, `=====` 구분선, 필드마다 툴팁, `Safe<T>` 같은 범용 헬퍼까지 들어 있었다.
기능은 많았지만 **팀원(UI 담당)이 읽고 이해하지 못했다.** 사용자 피드백: "너무 AI식 정리".

그래서 116줄로 다시 썼다:
- 기능을 **실제로 쓰는 4개**로 줄임 (안 쓰는 옵션 = 읽는 사람에게는 소음)
- 함수 이름만 봐도 흐름이 읽히게: `OnComboLanded` → `ShowCenter` / `Bounce` / `ShowNameUnderCells`
- 주석은 "왜"가 필요한 곳에만 (`SetUpdate(true)` 이유, "콤보는 항상 마지막 입력들로 완성된다")
- 범용 헬퍼 대신 그 자리에서 바로 보이는 `if (target == null) return;`

| 411줄 버전 | 116줄 버전 |
|---|---|
| 모든 경우를 대비 | 지금 필요한 것만 |
| 인스펙터 옵션 수십 개 | 연결할 칸 7개 |
| 쓴 사람은 뿌듯 | **읽는 사람이 바로 고칠 수 있음** |

> 코드는 쓰는 시간보다 **읽히는 시간**이 훨씬 길다. 팀 프로젝트에서 "좋은 코드" = 다음 사람이 겁 없이 고칠 수 있는 코드.
> 기능이 필요해지면 그때 추가하면 된다 (YAGNI: You Aren't Gonna Need It).

### 교훈 ②: 타격감은 UI가 아니라 로직에
예전엔 콤보 순간의 히트스톱·흔들림을 **UI 스크립트(`ElementComboHud`)** 가 걸었다. 지금은 **로직(`ElementComboChain`)** 이 건다:
```csharp
// ElementComboChain.cs:56 — "game feel, not UI"
[Header("Feel")]
[SerializeField] private float comboHitStop = 0.03f;
...
// AddInput: 콤보 완성 시
HitFeel.Play(comboHitStop, comboShake);
```
**왜 옮겼나?** 히트스톱은 "게임이 어떻게 느껴지나"(게임플레이)이지 "화면에 뭘 그리나"(UI)가 아니다.
UI에 두면 → UI 담당이 콤보 HUD를 지우거나 새로 만드는 순간 **콤보 타격감도 같이 사라진다.** 아무도 그걸 의도하지 않았는데.
→ 원칙: **기능(로직)과 표시(UI)를 섞지 마라.** UI는 지워도 게임이 똑같이 동작해야 한다.

## 4. 이펙트 (Fx) — 짧게

- 게임 코드는 `Fx.Hit(위치, 방향, 색, 큰가)`처럼 **"어디에, 얼마나, 무슨 색"** 만 말한다. 생김새는 프리팹이 정한다 (파사드).
- 이펙트 프리팹은 **오브젝트 풀**로 재사용 (`FxPrefabInstance`): 매번 Instantiate/Destroy하면 느리고 가비지가 생긴다. 끝난 이펙트는 꺼서 보관했다가 다시 켠다.
- 색만 바꿀 땐 `MaterialPropertyBlock` (SkillPickup에서도 사용): `renderer.material.color = ...`는 **머티리얼을 복제**해서 메모리가 늘고 배칭이 깨진다. 프로퍼티 블록은 공유 머티리얼은 그대로 두고 오브젝트별 값만 덮는다.

## 🎤 면접에서 이렇게 물으면

**Q. 타격감을 어떻게 구현했나요?**
> 히트스톱, 화면 흔들림, 방향성 카메라 킥 세 가지를 하나의 전역 클래스로 관리했습니다. 히트스톱은 timeScale을 0.05로 낮추고 현실 시간으로 종료를 재며,
> 여러 요청이 겹쳐도 더 강하거나 긴 쪽만 적용해 누적되지 않게 했습니다. 카메라는 추적 위치와 흔들림 오프셋을 따로 계산해서 마지막에 더하므로 흔들림이 추적에 섞이지 않습니다.
> 원거리 스킬은 명중과 무관하게 쏘는 감각이 필요해서 쏜 반대 방향으로 카메라를 밀어주는 킥을 추가했습니다.

**Q. 히트스톱 중에 UI는 어떻게 되나요?**
> 게임 시간에 맞춰 움직이면 UI도 같이 멈추기 때문에, UI 연출은 현실 시간으로 돌렸습니다. DOTween에서는 SetUpdate(true)로 timeScale을 무시하게 했습니다.

**Q. 머티리얼 색을 바꿀 때 주의할 점은?**
> renderer.material에 접근하면 머티리얼 사본이 생겨 메모리와 배칭에 불리해서, MaterialPropertyBlock으로 오브젝트별 색만 덮어썼습니다.
