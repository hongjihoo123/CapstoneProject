## 3. 왜 이렇게 나눴나 (설계)

### 3-1. 부모/자식 = Template Method 패턴
부모가 **순서(틀)** 를 정하고, 자식은 **다른 부분만** 채움.

```csharp
// 부모: "스킬 쓰면 → 시전 정보 만들고 → 자식한테 Cast 시킴" 이 순서는 고정
public sealed override ISkillExecution Begin(ISkillContext context) => Cast(new ElementSkillCast(this, context));
protected abstract ISkillExecution Cast(ElementSkillCast cast);   // ← 자식이 채우는 칸
```
- `sealed` = 자식이 Begin 을 못 바꿈 → 틀이 깨질 일 없음
- `abstract` = 자식이 Cast 를 **꼭** 만들어야 함 (안 만들면 컴파일 에러)

**처음엔 왜 하나였다가 나눴나:** 처음엔 SO 하나(`ElementSkillData`)에 모양 7개가 쓰는 칸을 다 넣었더니
메테오 인스펙터에 투사체 개수, 돌진 시간 같은 상관없는 칸이 다 보였음 → 복잡함.
모양별로 나누니까 **그 스킬이 쓰는 칸만** 보임.

### 3-2. 효과는 리스트 (조합)
메테오 = `[피해 45, 기절 1초]`, 바위 방패 끝 폭발 = `[피해 25, 밀치기 2.5]`.
새 조합 = 코드 안 고치고 인스펙터에서 리스트에 하나 더 추가.

### 3-3. 같이 쓰는 건 ElementSkillCast 에 몰아둠
7개 모양이 다 "맞으면 효과 + 이펙트 + 손맛" 을 해야 하는데, 이걸 각자 쓰면 7번 복붙.
→ `cast.Hit(적)` 한 줄이면 다 되게 모아둠. 손맛 바꾸고 싶으면 `Feel()` 한 군데만 고치면 15개 스킬 전부 바뀜.

### 3-4. CC 는 적이 처리 (책임 나누기)
스킬은 `ApplyStun(1초)` **요청만** 함. 진짜로 걸지 / 몇 초 걸지 / 어떻게 멈출지는 적이 정함.
- "남은 시간 vs 새 시간 큰 값" 규칙은 **남은 시간을 아는 적** 만 할 수 있음
- 스킬 두 개가 동시에 둔화 걸어도 적이 한 곳에서 정리하니까 안 꼬임
- 적 담당(JJH)이 자기 적에 `ICrowdControlTarget` 직접 만들면 그게 우선 → 서로 코드 안 건드림

## 6. 면접식 질문

**Q. 스킬 30개 넘게 어떻게 양산했어요?**
A. 스킬을 "판정 모양"과 "효과"로 나눴습니다. 모양은 7종이라 클래스 7개(부모 하나 상속)로 만들고,
효과(피해, 기절, 둔화 등)는 리스트로 조합합니다. 그래서 새 스킬은 대부분 코드 없이 ScriptableObject 에셋만 만들면 됩니다.

**Q. 왜 상속을 썼어요? 컴포넌트/전략 패턴도 있잖아요.**
A. 처음엔 전략 패턴 + SO 하나로 했는데, 모든 모양의 설정이 한 SO 에 다 보여서 기획자/팀원이 쓰기 어려웠습니다.
모양별로 SO 를 나누면 인스펙터에 필요한 칸만 보이고, 한 파일에 데이터와 동작이 같이 있어서 읽기도 쉬워서 바꿨습니다.
공통 흐름은 부모가 고정(`sealed Begin`)하고 자식은 `Cast` 만 채우는 Template Method 입니다.

**Q. CC 지속시간 겹치는 건 어떻게 처리했어요?**
A. 적 쪽 CC 모듈에서 `끝나는 시간 = Max(지금 끝나는 시간, 지금 + 새 시간)` 으로 처리합니다.
스킬은 요청만 하고 규칙은 적 한 곳에만 있어서, 스킬이 늘어나도 규칙은 한 군데만 고치면 됩니다.

**Q. 같은 적이 한 스킬에 여러 번 맞는 건 어떻게 막았어요?**
A. 스킬을 쓸 때마다 만드는 `ElementSkillCast` 가 `HashSet<IDamageable>` 로 이번에 맞은 적을 기억합니다.
장판처럼 일부러 여러 번 때리는 건 `HitAgain` 을 따로 씁니다.
