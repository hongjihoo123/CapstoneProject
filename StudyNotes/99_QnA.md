## A. 프로젝트 전반

**A1. 이 프로젝트에서 맡은 부분은?**
> 탑다운 액션 로그라이트에서 플레이어의 스킬 사용 레이어를 맡았습니다. 스킬 데이터와 실행 구조, 쿨다운, 스킬 교체, 원소 콤보 판정, 그리고 로직과 UI 사이의 경계(HUD 창구)를 설계했습니다.

**A2. 구조를 한 문장으로?**
> 스킬은 데이터(ScriptableObject)와 실행 객체로 나누고, 시스템 사이는 이벤트로 연결하며, UI는 창구 클래스 하나만 보게 해서 로직과 화면이 서로 독립적으로 바뀔 수 있게 했습니다.

**A3. 팀 작업에서 신경 쓴 것은?**
> 팀원 코드를 고치지 않고 확장하는 것과 병합 충돌을 줄이는 것입니다. 팀원의 원소 시스템은 기존 이벤트를 그대로 보내서 연결했고, 필요한 데이터는 리플렉션 대신 공개 함수를 요청했습니다. UI는 프리팹 단위로 나누고 참조를 코드가 스스로 찾게 해서 씬 파일을 동시에 고칠 일을 줄였습니다. → 04, 06장

## B. C# / 설계

**B1. 이벤트와 직접 호출의 차이, 왜 이벤트를 썼나?** → [01장 §1](01_CSharp기초.md)
> 직접 호출은 보내는 쪽이 받는 쪽을 다 알아야 합니다. 이벤트는 "스킬을 썼다"고 알리기만 하고 콤보·HUD·원소 시스템이 알아서 구독합니다. 덕분에 기능을 추가할 때 스킬 모듈을 고치지 않았습니다. 대신 구독 해제를 생명주기 짝에 맞춰 꼭 했습니다.

**B2. 인터페이스와 추상 클래스 언제 각각?** → [01장 §2](01_CSharp기초.md)
> "이 능력이 있니"만 중요하면 인터페이스, 공통 코드를 공유해야 하면 추상 클래스입니다. 스킬이 쓰는 도구 목록(ISkillContext)과 키 가로채기(ISkillInputInterceptor)는 인터페이스, 스킬 데이터의 공통 필드(SkillData)는 추상 클래스로 만들었습니다.

**B3. struct를 어디에 썼고 왜?** → [01장 §3](01_CSharp기초.md)
> UI에 넘기는 슬롯 정보(SlotInfo)와 쿨다운 스냅샷(SkillCooldownState)을 readonly struct로 만들었습니다. 둘 다 "그 순간의 값"이라 복사되는 게 맞고, 받은 쪽이 수정해도 원본에 영향이 없어야 했습니다. 작고 자주 만들어서 가비지도 줄어듭니다.

**B4. 싱글턴의 장단점과 사용처?** → [04장 §4](04_HUD경계와_설계원칙.md)
> HUD 창구에 썼습니다. 씬 연결 없이 어떤 UI 프리팹에서든 접근할 수 있는 게 장점이고, 전역 상태라 추적과 테스트가 어려운 게 단점입니다. 그래서 용도를 조회로 한정했고, 도메인 리로드를 끈 경우를 대비해 플레이 시작 때 static을 초기화합니다.

**B5. SOLID 하나를 예로?** → [04장 §6](04_HUD경계와_설계원칙.md)
> 의존성 역전: 스킬은 PlayerAgent가 아니라 ISkillContext 인터페이스에 의존합니다. 플레이어 쪽 구현은 어댑터 하나라서 플레이어 코드가 바뀌어도 스킬 20여 개는 그대로이고, 나중에 적에게 같은 스킬을 쓰게 할 수도 있습니다.

**B6. 파사드 패턴을 설명하고 예를 들어 주세요.** → [04장 §2](04_HUD경계와_설계원칙.md)
> 복잡한 여러 하위 시스템 앞에 단순한 창구 하나를 두는 패턴입니다. PlayerHudSource가 스킬 모듈·콤보·스킬 교체·캐릭터 정보를 모아 UI에 제공하고, 이펙트 호출용 Fx 클래스도 같은 역할입니다.

**B7. 의존 방향을 왜 신경 썼나?** → [04장 §5](04_HUD경계와_설계원칙.md)
> UI는 자주 바뀌고 로직은 덜 바뀌어서, 자주 바뀌는 쪽이 안정적인 쪽에 의존하게 했습니다(UI → 창구 → 로직). 순환 참조를 막고, 팀원과 파일이 겹치지 않아 충돌도 줄어듭니다. 원소 팔레트를 UI 폴더에서 원소 폴더로 옮긴 것도 로직이 UI를 참조하지 않게 하려는 것이었습니다.

**B8. 리플렉션의 위험은?** → [06장 §5](06_콤보시스템.md)
> 문자열로 멤버를 찾기 때문에 이름이 바뀌어도 컴파일 에러가 안 나고 실행 중에야 깨집니다. private을 뚫어 캡슐화를 깨고, 코드 스트리핑 시 멤버가 제거될 수 있으며 느립니다. 그래서 팀원에게 공개 읽기 함수를 요청해 제거했습니다.

## C. Unity

**C1. Awake / Start / OnEnable 차이와 각각 무엇을 하나?** → [02장 §1](02_Unity기초.md)
> Awake는 자기 준비, OnEnable은 켜질 때마다(이벤트 구독), Start는 첫 프레임 직전에 다른 오브젝트 참조를 가져오는 곳으로 씁니다. Start끼리는 순서가 보장되지 않아 HUD 창구는 처음 조회될 때 연결하는 지연 연결을 썼습니다.

**C2. ScriptableObject 주의점?** → [02장 §2](02_Unity기초.md)
> 모든 사용처가 하나의 에셋을 공유하고 에디터에선 플레이 후에도 값이 남아서, 런타임 상태를 넣으면 안 됩니다. 스킬 수치만 에셋에 두고 시전 상태는 시전마다 새로 만드는 객체에 뒀습니다.

**C3. [SerializeField] private vs public?** → [02장 §3](02_Unity기초.md)
> 인스펙터 편집은 허용하되 다른 코드가 함부로 바꾸지 못하게 해서 캡슐화를 지킵니다. 단, Unity가 직렬화하는 객체 안에서만 동작합니다.

**C4. Resources 폴더의 장단점?** → [02장 §4](02_Unity기초.md)
> 경로로 어디서든 로드할 수 있어 연결이 필요 없지만, 안 써도 빌드에 포함되고 경로 오타는 실행해야 압니다. 원소 팔레트 같은 전역 설정 하나에만 썼습니다.

**C5. 씬 파일 병합 문제를 어떻게 피했나?** → [02장 §5](02_Unity기초.md)
> 씬은 병합이 사실상 불가능해서 UI와 기능을 프리팹으로 나누고, 컴포넌트가 참조를 스스로 찾게 해서 씬에 저장되는 연결을 줄였습니다.

**C6. timeScale과 unscaledDeltaTime?** → [02장 §6](02_Unity기초.md), [07장](07_연출과_타격감.md)
> 히트스톱은 timeScale을 낮춰 구현하는데, UI까지 느려지면 안 되므로 UI 연출은 현실 시간(unscaled, DOTween의 SetUpdate(true))으로 돌렸습니다. 히트스톱 종료 시각도 현실 시간으로 잽니다.

**C7. Application.isFocused를 어디에 썼나?** → [02장 §7](02_Unity기초.md)
> 커스텀 조준 커서를 그리고 OS 커서를 숨기는데, 알트탭했을 때도 숨겨져 있으면 다른 프로그램에서 마우스가 사라진 것처럼 보입니다. 그래서 창이 포커스를 잃으면 조준 커서를 끄고 OS 커서를 돌려줍니다.

**C8. RuntimeInitializeOnLoadMethod(SubsystemRegistration)은 왜?** → [02장 §8](02_Unity기초.md)
> Enter Play Mode 설정에서 도메인 리로드를 끄면 static 값이 플레이 사이에 남습니다. 가장 이른 시점에 static을 초기화하는 함수를 9곳에 두었습니다. 현재 프로젝트는 리로드가 켜져 있지만, 누가 끄더라도 안전하도록 유지합니다. 팀원의 이벤트 채널 같은 ScriptableObject 안의 구독 목록은 리로드를 끄면 별도 정리가 필요합니다.

**C9. MaterialPropertyBlock은?** → [07장 §4](07_연출과_타격감.md)
> renderer.material은 머티리얼 사본을 만들어 메모리와 배칭에 불리합니다. 오브젝트별 색만 다르게 할 땐 프로퍼티 블록으로 공유 머티리얼 위에 값만 덮었습니다.

**C10. 오브젝트 풀링을 왜, 어떻게?** → [07장 §4](07_연출과_타격감.md)
> 이펙트를 매번 생성·파괴하면 비용과 가비지가 생겨서, 끝난 이펙트를 꺼서 보관했다가 재사용했습니다. 프리팹당 최대 개수를 두고 넘치면 가장 오래된 것을 재활용했으며, 외부 에셋이 스스로 파괴되는 설정을 꺼서 풀이 깨지지 않게 했습니다.

## D. 우리 시스템

**D1. 키를 누르면 스킬이 나가기까지?** → [03장 §1](03_스킬시스템.md)
> PlayerAgent가 매 프레임 스킬 모듈의 입력 처리를 부르고, 즉시 시전 키면 바로, 조준 키면 누르는 동안 범위를 보여주다 뗄 때 시전합니다. 시전하면 상태 머신이 그 슬롯 상태로 바뀌고, 스킬 데이터가 실행 객체를 만들어 매 프레임 진행합니다. 동시에 SkillUsed 이벤트가 나가 콤보와 UI가 반응합니다.

**D2. 쿨다운 구현?** → [03장 §6](03_스킬시스템.md)
> 충전식이고, 남은 시간이 아니라 다음 충전이 끝나는 절대 시각을 저장해서 조회할 때 계산합니다. Update가 필요 없고, 스킬을 바닥에 내려놔도 시간이 흐르는 효과가 자연스럽게 생깁니다.

**D3. SkillReady 이벤트는 왜 로직에서 감지하나?** → [03장 §7](03_스킬시스템.md)
> "못 씀 → 씀" 변화 감지를 UI마다 구현하면 중복되고 어긋날 수 있어서, 스킬 모듈이 매 틱 한 번 감지해 사건으로 알려줍니다. UI는 반응만 합니다.

**D4. 스킬 교체 시 키 충돌은?** → [05장 §3](05_스킬교체.md)
> 스킬 모듈에 입력 가로채기 인터페이스를 두고, 교체 기능이 Q/E를 빌려 갑니다. 가로챈 키는 원래 입력을 감싼 객체에서 "안 눌림"으로 보이게 해서 스킬이 나가지 않습니다.

**D5. 그 과정의 버그와 해결?** → [05장 §4](05_스킬교체.md)
> 교체 처리 중 교체 창이 닫히면서 같은 프레임 뒤쪽 코드가 키를 다시 눌린 것으로 봐서 새 스킬이 바로 나갔습니다. 이번 프레임에 넘긴 키를 배열에 기록해 프레임 끝까지 숨기는 것으로 해결했습니다.

**D6. 교체해서 쿨다운을 건너뛰는 꼼수는?** → [05장 §6](05_스킬교체.md)
> 쿨다운을 스킬과 함께 옮기고, 들어온 스킬은 1초 잠금을 걸었습니다. HUD는 잠금이 쿨다운보다 길면 잠금을 보여줍니다.

**D7. 콤보 판정 알고리즘?** → [06장 §3](06_콤보시스템.md)
> 최근 입력의 끝부분이 레시피의 앞부분과 몇 칸 겹치는지 검사합니다. 전체 길이만큼 겹치면 완성이고 가장 긴 레시피가 우선입니다. 덜 겹친 경우는 진행도로 다음 원소를 안내합니다. 규모가 작아 단순 비교를 택했습니다.

**D8. PlayerHudSource를 1분 안에 설명해 보세요.** → [04장](04_HUD경계와_설계원칙.md)
> UI가 보는 유일한 창구입니다. 조회 함수로 슬롯 정보를 계산된 값(struct)으로 주고, 로직 이벤트를 받아 UI용 이벤트로 다시 발행합니다. 씬 연결 없이 싱글턴으로 찾고, 초기화 순서 문제는 처음 조회될 때 연결하는 방식으로 풀었습니다. 콤보가 없는 씬처럼 기능이 없으면 빈 값과 무발행으로 조용히 넘어갑니다. 그래서 로직이 바뀌어도 UI는 안 깨지고, UI 담당은 로직을 몰라도 됩니다.

**D9. 타격감은?** → [07장](07_연출과_타격감.md)
> 히트스톱, 흔들림, 방향 킥을 한 클래스에서 관리하고 겹치면 강한 쪽만 적용합니다. 카메라는 추적 위치와 흔들림을 분리해 더합니다.

**D11. 동작하는 코드를 왜 다시 썼나요?** → [07장 §3](07_연출과_타격감.md)
> 콤보 연출 파일이 모든 경우를 대비해 구역·옵션·범용 헬퍼로 400줄이 넘었는데, UI 담당 팀원이 이해하지 못해 쓸 수 없었습니다. 실제로 쓰는 연출만 남겨 100줄 남짓으로 다시 썼고, 함수 이름만 보고도 흐름이 읽히게 했습니다. 팀에서는 다음 사람이 고칠 수 있는 코드가 좋은 코드라는 걸 배웠습니다.

**D12. 히트스톱을 UI에서 로직으로 옮긴 이유는?** → [07장 §3](07_연출과_타격감.md)
> 히트스톱은 게임 느낌이라 게임플레이 쪽 책임인데 UI 스크립트에 있었습니다. 그러면 UI를 교체하거나 지울 때 타격감도 같이 사라집니다. 콤보 판정 클래스로 옮겨서 UI와 무관하게 동작하게 했습니다.

**D10. 대시 방향은 어떻게 정하나?** → [03장 §8](03_스킬시스템.md)
> 이동 키를 누르고 있으면 그 방향, 아니면 마우스 조준 방향입니다. 공용 함수 하나로 만들어 대시와 블링크가 같이 씁니다.

## E. 마무리 질문 대비

**E1. 다시 만든다면 바꾸고 싶은 것은?**
> 기존 UI 일부가 아직 로직을 직접 참조하고 있어서 모두 창구를 통하게 옮기고 싶습니다. 그리고 콤보 판정 같은 순수 로직에는 EditMode 테스트를 붙이고 싶습니다. 처음부터 어셈블리 정의(asmdef)로 UI·창구·로직을 나눴다면 의존 방향을 컴파일러가 강제해 줬을 것입니다.

**E2. 이 프로젝트에서 가장 많이 배운 것은?**
