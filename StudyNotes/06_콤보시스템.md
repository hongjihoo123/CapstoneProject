## 1. 규칙 (격투게임 콤보처럼)

- 원소 스킬(Q, E)을 쓸 때마다 **입력 1개** (불·물·바람·전기·땅). 원소 없는 스킬(대시, 무기 스킬, R)은 입력이 아니다.
- 3초(`chainWindow`) 안에 다음 원소 스킬을 쓰면 체인 유지, 넘기면 끊김(BREAK).
- **최근 입력의 끝부분이 콤보표의 레시피와 같아지는 순간 즉시 발동.**
- 입력은 소비되지 않는다 → 콤보끼리 겹치고 이어질 수 있다.
- 발동한 콤보는 **스톡**(서로 다른 것 최대 3개). **R**을 쓰면 스톡 전부 강화 발동 = **FINISH**.
- 콤보표 자체는 팀원 JJH의 `ElementBuffController` 인스펙터에 있다.

## 2. 구조

```
 SkillStateModule.SkillUsed
        │
        ▼
 ElementComboChain  (입력 기록 + 3초 타이머 + 스톡)
        │ 소유
        ├──▶ ElementComboBook  (레시피 목록 + 매칭 함수)  ◀── JJH ElementBuffController에서 1번 읽음
        │
        ├── 이벤트: InputAdded / ComboLanded / ChainBroken / StockChanged / FinisherReleased
        │        └──▶ PlayerHudSource ──▶ UI (04장)
        │
        └── JJH 이벤트 채널로 ElementBuffTriggeredEvent 발행 ──▶ JJH가 버프 처리
```

- **Book = 규칙집**(데이터 + 순수 계산), **Chain = 진행자**(상태 + 타이머 + 이벤트). 단일 책임 원칙.
- Book은 MonoBehaviour가 아닌 **일반 클래스** → Unity 없이도 테스트 가능.

## 3. 판정 알고리즘 🔴

입력은 최근 4개(`maxInputs`, 최소 = 가장 긴 레시피 길이)만 유지. 꽉 차면 가장 오래된 것을 버린다 (**슬라이딩 윈도우**).

### (1) 끝부분 매칭 `TailMatches(inputs, length)`
**"입력의 마지막 length개 == 레시피의 처음 length개?"**

```csharp
int offset = inputs.Count - length;       // 입력에서 비교를 시작할 위치
for (int i = 0; i < length; i++)
    if (inputs[offset + i] != Sequence[i]) return false;
return true;
```

```
inputs   = [땅, 불, 물, 바람]          length = 3 → offset = 1
                ↓   ↓   ↓
Sequence =     [불, 물, 바람]          → 일치!
```

비유: 휴대폰 잠금 패턴이 아니라 **도어락 비밀번호**. 앞에 아무 번호나 눌렀어도, 마지막 4자리가 맞으면 열린다.

### (2) 완성 = 레시피 전체 길이만큼 끝이 일치
```csharp
public bool EndsOn(inputs) => TailMatches(inputs, Sequence.Length);
```

### (3) 동시에 여러 개가 맞으면 → 가장 긴 것
`[바람]`과 `[불,물,바람]`이 동시에 맞으면 3개짜리. 긴 콤보를 노린 플레이어 의도를 존중.

### (4) 진행도 `TailProgress` — "이 레시피 지금 몇 칸째?"
```csharp
for (int k = Mathf.Min(inputs.Count, Sequence.Length - 1); k > 0; k--)   // 큰 것부터 내려감
    if (TailMatches(inputs, k)) return k;
return 0;
```
- 상한이 `Length - 1`: **완성된 건 진행 중이 아니다.** 그리고 다음 칸 = `Sequence[progress]`를 안전하게 꺼낼 수 있다(progress가 Length면 배열 밖).

레시피 `[불, 물, 바람]`일 때:

| 입력 끝부분 | k=2 (`불,물`?) | k=1 (`불`?) | 진행도 | 다음에 누를 것 |
|---|---|---|---|---|
| `[땅]` | ✗ | ✗ | 0 | — |
| `[땅, 불]` | ✗ | ✓ | 1 | 물 |
| `[불, 물]` | ✓ | — | 2 | 바람 |
| `[물, 불]` | ✗ | ✓ | 1 | 물 |

### (5) 안내할 레시피 고르기 `TryFindBestProgress`
1순위 진행도가 큰 것, 동률이면 2순위 **짧은 레시피**(완성까지 덜 남은 것). → UI의 "NEXT" 칸.

### 시간 복잡도
레시피 R개, 길이 최대 L → 대략 O(R × L²). 입력 4개, 레시피 수십 개라 아무 문제 없다.
문자열 알고리즘(KMP, Aho-Corasick)으로 더 빠르게 할 수 있지만 **이 규모에선 단순한 게 읽기 쉽고 충분히 빠르다** = 규모에 맞는 선택.

## 4. 이벤트 순서 예시

콤보표: `증기 = [불, 물]`. Q=불, E=물.

```
Q(불)  → InputAdded   inputs=[불]           콤보 없음
E(물)  → InputAdded   inputs=[불,물]
       → 증기 완성! HitFeel(살짝) → ComboLanded(증기) → JJH에 이벤트 → 스톡 [증기] → StockChanged
R      → 원소 없음 → 입력 아님. 하지만 finisherSlot이므로 → FinisherReleased([증기]) → 스톡 비움
(3초 동안 원소 스킬 없음) → ChainBroken(2)
```

**"비우기 전에 발행"**: `FinisherReleased`는 스톡을 **복사한 리스트**를 넘기고 그다음 원본을 비운다. `ChainBroken`도 입력을 지우기 전에 발행. 구독자가 이벤트 안에서 값을 읽을 때 아직 남아 있어야 연출을 그릴 수 있다.

## 5. 리플렉션을 왜 없앴나

### 리플렉션이란
코드가 **실행 중에** 다른 클래스의 필드·함수를 "이름(문자열)으로" 찾아서 접근하는 기능. `private`도 뚫을 수 있다.

### 예전 코드
JJH의 콤보표는 `private` 필드였다. JJH 코드를 안 고치려고 리플렉션으로 읽었다:
```csharp
// 예전 (지금은 없음)
FieldInfo f = typeof(ElementBuffController).GetField("combos", BindingFlags.NonPublic | BindingFlags.Instance);
object combos = f.GetValue(controller);
... type.GetField("name") ... type.GetField("sequence") ...
```

### 위험한 이유
| 위험 | 설명 |
|---|---|
| **컴파일러가 못 잡는다** | JJH가 `combos`를 `comboList`로 이름만 바꿔도 빌드는 성공. 게임을 실행해야 "콤보가 전부 사라짐"을 알게 된다 |
| **캡슐화 파괴** | private은 "내 맘대로 바꿀 거니 건드리지 마"라는 약속. 그걸 몰래 뚫으면 JJH는 내가 의존하는지 모른 채 고친다 |
| **빌드 환경 문제** | IL2CPP / 코드 스트리핑(쓰이지 않는 코드 제거) 때 문자열로만 참조된 멤버는 지워질 수 있다 |
| **느림** | 일반 접근보다 훨씬 느리다 (우리는 Awake 1번이라 큰 문제는 아니었음) |
| **읽기 어려움** | "이 필드를 누가 쓰나?" 검색해도 문자열이라 안 나온다 |

### 지금 코드 — JJH에게 공개 읽기 함수를 추가받음
```csharp
// JJH ElementBuffController.cs:47-49 (JJH 코드에 추가된 공개 접근자)
public int ComboCount => combos != null ? combos.Length : 0;
public string GetComboName(int index) => combos[index].name;
public IReadOnlyList<ElementType> GetComboSequence(int index) => combos[index].sequence;

// 우리 ElementComboBook.From
for (int i = 0; i < controller.ComboCount; i++)
{
    string name = controller.GetComboName(i);
    IReadOnlyList<ElementType> source = controller.GetComboSequence(i);
    var sequence = new ElementType[source.Count];   // 복사해서 보관 (원본을 우리가 못 바꾸게)
    ...
}
```
- 이제 JJH가 이름을 바꾸면 **컴파일 에러** → 바로 안다.
- `IReadOnlyList` → 우리가 JJH의 콤보표를 실수로 수정할 수 없다.
- 교훈: **남의 코드 내부가 필요하면 리플렉션으로 뚫지 말고, 공개 API를 부탁하라.** (팀 협업의 기본)

## 6. JJH 이벤트 채널과의 연결

- 콤보가 발동하면 `systemChannel.RaiseEvent(SystemEvents.ElementBuffTriggeredEvent.Init(combo.Sequence))`.
- JJH 쪽은 원래 "3초 뒤 쌓인 원소로 버프"였는데, 우리 체인이 **같은 이벤트**를 보내니 JJH 코드는 바뀐 걸 모르고 그대로 동작.
- `SystemEvents.ElementBuffTriggeredEvent`는 **static 인스턴스 하나를 `Init()`으로 재사용**(매번 new 안 함 → 가비지 없음). 이벤트가 동기(바로 처리)라서 피니시에서 연속 발행해도 안전.

## 🎤 면접에서 이렇게 물으면

**Q. 콤보 판정은 어떻게 하나요?**
> 최근 입력을 최대 N개 유지하고, 새 입력이 들어올 때마다 각 레시피에 대해 "입력의 마지막 k개가 레시피의 처음 k개와 같은지"를 검사합니다.
> k가 레시피 길이면 완성이고, 여러 개가 완성되면 가장 긴 레시피를 고릅니다. 완성 전이면 가장 많이 진행된 레시피를 찾아 다음에 눌러야 할 원소를 UI에 보여줍니다.
> 입력과 레시피 수가 작아서 KMP 같은 알고리즘 대신 단순 비교를 택했습니다.

**Q. 리플렉션을 썼다가 뺐다고 했는데, 왜죠?**
> 팀원 코드의 private 콤보표를 이름 문자열로 읽었는데, 필드 이름이 바뀌어도 컴파일 에러가 나지 않고 실행해야만 깨진 걸 알 수 있었습니다.
> 캡슐화를 깨는 것이기도 해서 팀원에게 읽기 전용 공개 함수를 추가해 달라고 했고, 이제는 이름이 바뀌면 컴파일 단계에서 바로 드러납니다.

**Q. 팀원 시스템과 어떻게 연결했나요?**
> 팀원의 원소 시스템이 원래 받던 이벤트를 그대로 보내도록 해서, 팀원 코드 수정 없이 판정 방식만 교체했습니다. 콤보표도 팀원 인스펙터 값을 그대로 읽어서 값이 두 군데로 나뉘지 않게 했습니다.
